# 导入数据 · 外部软件键名映射方案

> 解决的问题：从支付宝/微信账单、随手记、鲨鱼记账、钱迹等其他软件导出的 CSV/Excel，
> 表头叫法和我们的字段名不一致（"交易时间" vs "日期"、"金额(元)" vs "金额"…），
> 值的写法也五花八门（`¥1,234.56`、`2026/7/4 12:03`、Excel 日期序列号…）。
>
> 实现位置：`cloudfunctions/api/dataio.js`（纯逻辑，可本地单测）+ `handlers.js` 的 `data.import`。
> 测试：本地回环测试 28 项全过（导出→导入 CSV/Excel/JSON、支付宝样本、脏值、坏行反馈）。

---

## 一、总体思路：三层归一化管道

任何来源的文件都先被解析成「原始行对象数组」，再经过统一管道压成我们的规范行：

```
文件 (json/csv/xlsx)
  → 解析层     parseCsv / excelToRows / JSON.parse      （只管格式，不管语义）
  → 键名映射层  mapKeys + ALIASES                        （别名表头 → 规范字段）
  → 值归一化层  normType/normAmount/normDate/normCurrency/normCategoryPath
  → { rows: 规范行[], errors: [{index, reason}] }        （逐行反馈，坏行不悄悄丢）
  → data.import：分类匹配 + 汇率补齐 + 批量入库
```

规范行字段：`{ type, amount, date, currency?, categoryPath?, title?, note?, amountConverted?, rate? }`

## 二、键名映射层（ALIASES）

表头做 `trim + toLowerCase` 后查别名表；**未知列直接忽略**（不报错），同一字段命中多列时取第一个。

| 规范字段 | 支持的表头别名 |
|---|---|
| date | date、日期、时间、交易时间、记账日期、交易创建时间、日期时间、入账日期、消费日期 |
| type | type、类型、收支、收/支、收支类型、交易类型 |
| amount | amount、money、金额、原始金额、金额(元)、金额（元）、交易金额、消费金额 |
| currency | currency、币种、货币、币别 |
| category | categorypath、category、分类、类别、分类名称、交易分类、一级分类、父类别、支出类别、收入类别 |
| subcategory | subcategory、二级分类、子分类、子类别 |
| title | title、标题、名称、商品、商品名称、项目 |
| note | note、remark、memo、description、备注、摘要、说明、商品说明 |
| amountConverted | amountconverted、换算金额 |
| rate | rate、汇率 |
| counterparty | 交易对方、对方、收/付款方（备注为空时兜底填入备注） |

**扩展方式**：以后遇到新软件的表头，在 `dataio.js` 的 `ALIASES` 对应数组里加一个别名即可，其余管道零改动。

## 三、值归一化层

| 字段 | 清洗规则 |
|---|---|
| type | 收入/收/income/in/+ → income；支出/支/expense/out/-/消费 → expense；**空 → 默认支出**；其他（不计收支/转账等）→ **整行跳过并记录原因** |
| amount | 去 `¥￥$€£ , 空格 元` 后 parseFloat，取绝对值（正负号交给 type）；非数字 → 跳过 |
| date | 支持 `YYYY-MM-DD`、`YYYY/M/D`、`YYYY.M.D`、`YYYY年M月D日`、`YYYYMMDD`、带时间后缀（截断）、Excel 日期序列号（20000~80000 判定）、JS Date 对象；范围校验 1970~2100；无法识别 → 跳过 |
| currency | 3 字母码转大写；中文名映射（人民币→CNY、美元→USD、欧元→EUR、日元→JPY、港币→HKD、英镑→GBP、韩元→KRW）；识别不了置空（后续按账本基准币处理） |
| categoryPath | 单列含 `/ > ＞` 分隔的拆开重排为「父 / 子」；有独立"二级分类"列时拼成「父 / 子」 |

## 四、入库阶段（data.import）

1. **分类匹配与自动创建**（收/支各自集合内，互不串）：
   - 匹配顺序：「父 / 子」全路径精确匹配 → **末级名**匹配（并入账本已有结构，避免重复建树）→ **自动创建**。
   - 自动创建默认开启（`autoCreateCategories: false` 可关）：一级不存在则建一级（icon=dots），二级不存在则建在对应一级下；同次导入内有缓存，不会重复建。新建数量随结果返回并在前端提示"自动新建分类 N 个"。
   - 关闭自动创建时未匹配 → `categoryId=null`，但**保留原分类文字**作 categoryPath 快照（不乱归类，历史可读）。
2. **分类层级归一**（我们的模型固定两级）：
   - 只有一级 → 作为一级分类；
   - 「分类 + 子分类」两列 → 「父 / 子」；
   - **3~4 级路径**（`a/b/c/d`）→ 折叠为「首级 / 末级」（首级定大类、末级最具体，中间层舍弃）。
3. **金额列策略**：
   - 只有一个金额列（无"换算金额"）：金额视为**该行币种的原始金额**；币种列缺失/识别不了则按账本基准币（rate=1）。
   - 原始金额 + 换算金额都有：都保留，并用「换算 ÷ 原始」反推当日汇率（保持原软件的固化值）。
   - **只有"换算金额"列**（无原始金额）：把它当作**基准币金额**入账（此时即使标了外币也无法还原原始外币值，按基准币最不失真，币种强制置基准币）。
4. **汇率补齐**（外币行）：行内 `rate` → 「换算 ÷ 原始」反推 → 查 `rates` 当日快照；都取不到则该行失败并给原因。
5. **批量入库**：100 条/批 `add({data:[...]})`，避免逐条 await 超时。记录人/付款人 = 导入者；补齐 `createdBy/updatedAt/updatedBy` 审计字段。
6. **结果反馈**（PRD 要求）：返回 `{ success, failed, createdCategories, reasons[≤8] }`，前端弹窗展示"成功 N 条，失败 M 条，自动新建分类 K 个 + 每条原因"。

## 五、边界与已验证用例

- 备注含逗号/引号/换行的 CSV（RFC4180 转义）回环无损；
- 我们自己导出的 CSV/Excel/JSON 三格式**全字段回环一致**（含 rate 透传）；
- 支付宝风格账单：`交易时间/收支/金额(元)/交易分类/商品说明/交易对方` 正确映射，`不计收支` 行跳过且原因可读；
- Excel 序列号日期（45113 → 2023-07-06）、`usd`→USD、`人民币`→CNY；
- 坏行（缺日期/金额非法/日期越界 2026-13-40）全部拒收且逐条给原因。

## 六、已知限制 / 后续可做

- 微信/支付宝官方账单 CSV 头部有几行"说明文字"再才是表头——当前解析假设第一行就是表头，这类文件需先手工删掉前置说明行（后续可做：自动探测表头行）。
- 别名表靠人工维护；量大后可做"首行预览 + 手动列映射"向导（P3 批量导入向导的一部分）。
- Excel 只读第一个工作表。
